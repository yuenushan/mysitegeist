01总览：MCP 客户端是怎么"够到"浏览器的

结论：工具不搬进 Node，桥只是转发器——sidepanel 把自己的 AgentTool 目录用 hello 上报，桥原样透出为 tools/list；调用在扩展进程里执行，所以权限弹窗、confirm 语义与侧栏内完全一致。

03一次 tools/call 的旅程

结论：请求最多经一跳 HTTP（proxy→master），执行永远发生在扩展里；取消（用户 ESC 或 120s 超时）会一路转成 AbortSignal，迟到结果被丢弃。

  1. pi → 桥（stdio） tools/call {name, arguments}；pi 侧每请求超时 120s（mcp.json timeout: 120）
  2. proxy → master（可选一跳） 重编号 p-<nonce>-<n> 后 POST /rpc；master 按 id 精确匹配取消与回包
  3. master → sidepanel（WebSocket） {type:"call", id, tool, args}；无面板连接时立即返回 isError: true 的明确提示
  4. sidepanel 分发 按 name 找工具；先跑 prepare 钩子（如 extract_image 按当前窗口定 windowId），再 tool.execute(id, args, signal)
  5. 结果回传 {type:"result", ok, content, details} → master 组装 MCP 响应：content 透传（文本/图片），details 作为 structuredContent；失败转 isError
  6. 取消路径 pi notifications/cancelled → 桥回放 {type:"abort", id} → 面板 controller.abort()；取消后的迟到结果直接吞掉不回包

05自愈与重连时序

结论：所有断线都靠指数退避 + 自动接管兜底，无需人工干预；唯一前提是 sidepanel 开着。

bridge 未运行 面板按 1s → 2s → 5s → 10s → 30s 封顶持续重连；Settings → MCP Bridge 显示 "Waiting for bridge..."
pi 会话启动 / 热重载 spawn bridge：端口空闲 → 直接 master；被占 → 探测 /health（1500ms 超时）→ 是 sitegeist 就做 proxy；占用者非 sitegeist → 重试 ~15s 后退出并报错
面板连上 hello 上报 9（或 10）个工具 → master 发 tools/list_changed → pi 刷新工具列表
master 被杀 / 崩溃 proxy 轮询（5s）失败 → /health 确认 → 抢绑端口升级为新 master；面板 ≤30s 重连，目录恢复
面板关闭 WS 断开；in-flight 调用立即收到 "panel disconnected" 错误；新调用返回明确提示，直到面板再次打开
